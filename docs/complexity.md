# 复杂度与性能模型

miniGit 是教学实现，优先保证格式清晰和算法可读性。下面的复杂度帮助读者理解性能瓶颈来自哪里。

设：

- `B` 是被读取文件的总字节数
- `N` 是索引条目数
- `V` 是提交数量
- `E` 是 Commit parent 边数量
- `F` 是工作区扫描到的文件数量

## 对象读写

| 操作 | 时间复杂度 | 额外空间 |
|---|---:|---:|
| 写入一个 Blob | `O(B)` | `O(B)` |
| 读取一个对象 | `O(B)` | `O(B)` |
| 计算一个文件 SHA-1 | `O(B)` | 取决于对象序列化和压缩缓存 |

zlib 压缩和解压缩都需要处理完整对象，因此对象大小直接影响运行时间和内存。

## 索引

读取索引需要扫描所有条目，因此是 `O(N + total_path_bytes)`。当前实现把完整索引读入内存，并逐条解析，所以额外空间也是 `O(N + total_path_bytes)`。

写入索引同样需要写出全部条目，而不是只更新一个条目。

## `add`

对多个文件执行 `add` 时，哈希和写 Blob 的成本与这些文件内容总大小 `B` 成正比；索引还会被读取和整体写回，因此还有 `O(N)` 的索引成本。

## Tree 构造

构造 Tree 需要遍历索引条目，并为每个目录生成一个 Tree 对象。目录内排序的总成本通常可近似为 `O(N log N)`；序列化路径和对象 ID 的成本是线性的。

## `status`

`status` 需要展开 HEAD Tree、遍历索引、扫描工作区，并对元数据发生变化的文件重新计算 Blob SHA-1。若工作区有 `F` 个文件，索引有 `N` 个条目，重新哈希的内容大小为 `B_changed`，可近似为：

```text
O(F + N + B_changed)
```

## 引用解析

直接引用解析通常是常数次文件读取；短哈希解析需要扫描对应前缀目录中的候选对象。

## 提交历史

`log` 对提交图做一次 DFS，时间复杂度是 `O(V + E)`，`seen` 集合需要 `O(V)` 空间。

## 设计取舍

当前实现选择直接扫描文件系统、整体读写索引、使用 loose object 和 Python 容器。这些选择让算法容易阅读和调试，但在大型仓库上会明显慢于真实 Git 的文件监视器、packfile、增量索引和缓存机制。
